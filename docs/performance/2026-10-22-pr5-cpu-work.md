# PR5 CPU preparation measurements and validation

Measured 22 October 2026 in test0-01; base 2444228.

## Result and limits

Main-addon cold preparation is cooperative and cancellation-aware. One OnUpdate
queue shares a 0.65 ms clock deadline, leaving headroom toward the approximately
1 ms background target; it polls after bounded units and has a hard step cap.
There are at most 16 jobs and 16 subscribers per shared profession preparation.
The driver removes OnUpdate when the queue empties. No permanent ticker is added.

The initial timing targets are **not fully met across all stress samples**.
Measured cooperative frames reached 5 ms, and the 250 x 4,096 prepared atomic
save reached 10 ms. Normal GC is included and the standalone timer resolves only
about 1 ms. Cooperative deadlines cannot interrupt a Lua allocation, GC step,
API call, codec call or atomic completion. Do not interpret the configured
0.65 ms deadline as a measured hard upper bound.

The queue covers main-addon preparation. Gear and Bank retain their existing
independent bounded/event-driven behavior; this probe does not establish a 1 ms
combined budget for all three addons. In-game combined login/sync/browsing/bank,
combat, frame-time spikes and memory-stabilization measurements remain outstanding.
This commit must not be used to claim an in-game FPS improvement or to close
issue #94's remaining live-validation criteria.

## Baseline and methodology

The selected baseline contains PRs 1–4 and profession compression. It uses
P5 / GC_PROF5 and gear protocol 6; gear compression PR #93 is not in this worktree.
No codec, wire format, SavedVariables global or schema was changed.

Before edits: 861 regression tests passed and 42 TOC-listed Lua sources compiled.
Five-sample synchronous baseline medians were:

| Dense fixture | Catalog cold/warm ms | Digest cold/warm ms |
| --- | ---: | ---: |
| 10 x 500 | 4 / 2 | 8 / 2 |
| 50 x 1,000 | 37 / 15 | 79 / 15 |
| 100 x 2,000 | 160 / 60 | 387 / 57 |

`tests/bench_cpu_slices.lua` runs five samples per size in the bundled Windows
Lua 5.1 runtime, using os.clock CPU milliseconds. Fixtures give every character
every recipe: these are dense scaling probes rather than typical-guild data.
Fixture construction and forced collection are outside timing; normal GC remains
on. Digest and catalog jobs run concurrently in the same queue. Each frame timing
covers the complete RunCPUFrame call. Completed hashes/models are checked against
complete synchronous results. Recipe filtering and actual queued unchanged-roster
validation are then measured, followed by ordinary and prepared atomic saves.
The token preparation cost is not included in prepared-commit timings: production
UI/record paths prepare it cooperatively before calling the synchronous save.

At 60 frames/second, the median 610-frame 100 x 2,000 combined preparation probe
would occupy about ten seconds of spare-frame work; the stress probe can take
roughly 52 seconds. A protocol response whose fixed deadline expires before
preparation finishes is cancelled rather than extending its deadline. More work
per frame would improve throughput at the cost of the frame target. No claim is
made that every stress peer can respond before its existing response deadline.

## Compatibility and correctness

Public synchronous builders and storage functions still return complete results.
UI/events prepare captures, catalogs, filters and validation first. A changed
profession clears obsolete clickable rows while preparing the new catalog; an
unchanged view retains its prior completed model. Hidden/inactive, superseded,
revision-changed, guild/session-changed and database-replaced work cannot publish.

Validation reuse is an opaque, identity-bound, single-use operation proof. Full
index validation happens during preparation. Consumption verifies revision and
table identities; the synchronous save rechecks the exact controlled invalidation
sequence before mutation. Forged, reused, stale and replaced-input proofs fall
back to full validation. The proof supports ordinary exact-identity/new-GUID
saves. Rename/repair paths retain full recovery validation; tests exercise those
paths with the real frame driver. Capture validation, freshness, ownership,
codec limits and post-storage ACKs remain in place. Read jobs preserve repair
flags, including when cancelled midway through full validation.

Membership writes avoid removing/reinserting unchanged memberships and use binary
search only after the existing strictly-sorted membership invariant is validated.
Sole-owner label/icon replacement keeps its previous semantics. Dense catalogs
sort the shared owner order once; manifest preparation sorts recipe IDs once and
shares temporary immutable recipe descriptors across character captures.

Presence-only roster events refresh recipient availability without invalidating
unchanged membership calculations/catalogs. Full saved-index validation runs in
the queue; unchanged results consume their proof without repeating synchronous
registry scans. Changed rosters apply after validation; registry recovery retains
the full original path. Changed membership, recovery and ordinary public
synchronous entry points can still exceed interactive targets on large caches.

## Comparable synchronous and wire probes

The final catalog probe measured cold/warm medians of 5/3, 38/21 and 149/80 ms for
10 x 500, 50 x 1,000 and 100 x 2,000. It retains complete public synchronous reads,
so these are total costs, not per-frame slice times. Warm reads do no date work;
models and shared owner descriptors are reused.

The final sync probe's current 100 x 2,000 cold/warm digest medians were 265/69 ms.
Compared with the selected baseline's 387/57 ms, cold work fell while mandatory
synchronous validation/checkpoint overhead increased the warm total. Production
prepared revisions avoid repeating that warm global read within an operation.

The equal 10 x 500 exchange still used 3 frames / 187 bytes. The compressed
2,000-recipe exchange still used 48 frames / 10,165 bytes. The representative
37,026-byte record encoded to 363 bytes. Encode median was 3 ms; decode rounded
to 0 ms at this timer resolution. Codec work remains bounded and synchronous.
These results verify wire equivalence and convergence, not live delivery/FPS.
