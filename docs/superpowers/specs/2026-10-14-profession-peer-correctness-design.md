# Profession peer correctness

The user approved including the Alice/Bob correctness case in PR #52 and staying on Improved-struc. Matching one peer must not prevent a manual request from consulting another peer holding newer data.

Use the existing P3 protocol and selected-peer whispers. A manual request owns a finite comparison operation: try at most four distinct eligible guild peers in total, one at a time, respecting existing cooldowns. Prioritize known participating peers initially, then rotate the candidate window across separately requested operations so a stable roster cannot permanently strand peers beyond the first four. Rotation never creates work by itself. Every subsequent request names its preferred peer so no other client supplies its full manifest. Do not retry unavailable peers, discover indefinitely, or promise guild-wide agreement. Older compatible clients can still participate without a new wire protocol.

The initial comparison can retain responder election. Following comparisons must consult the bounded candidate list even if Alice initially matches; a different hash does not establish which cache is newer. Directed requests must not consume bystander session slots, while existing backoff for meaningful save-created work still prevents storms. Candidate start failures count as uncertainty. Existing original capture timestamps, conflicts, local ownership checks, record limits, transport failure behavior, and cached-data labels remain authoritative. A finite budget or uncertainty must leave an honest catch-up status, and later failure must not hide an already established conflict. Cancellation, guild changes, failure, combat, and the operation deadline discard dependent jobs.

Project policy takes precedence over existing README exceptions: remove login digest broadcasts and recurring 5–7 minute background announcements/comparisons. Timers may pace work already created by an explicit request or meaningful snapshot change; elapsed time alone must create no traffic. Do not implement grouped hashes or new game-state sources.

Test first: Alice is behind the requester and Bob ahead; Alice matches while Bob is ahead; bounded many-peer work; matching/duplicate snapshots avoid repeated full transfers; unavailable peers and cancellation; idle/login silence. Existing tests must be adapted to request-driven semantics and the full Lua suite must pass.

Policy basis: Blizzard UI Add-On Development Policy, https://us.forums.blizzard.com/en/wow/t/ui-add-on-development-policy/24534 (checked 2026-10-14), prohibits negatively impacting players/realms and cites excessive chat usage. This design is a conservative project choice, not an official endorsement of a particular protocol. Existing secret-value/combat guards remain intact; no new API, external acquisition, or legal interpretation is introduced.
